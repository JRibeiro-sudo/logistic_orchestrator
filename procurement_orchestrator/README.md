# Procurement Material Recovery Orchestrator (Prototype)

> **This is a synthetic academic prototype**, built for an Executive MBA
> assignment (Strategic Innovation in the Age of AI). Every supplier name,
> part number, cost figure, and dataset in this repository is fictional —
> generated by `generate_mock_data.py` — and is not real Bosch Home Comfort
> data, a real Bosch supplier, or a real figure. All enterprise integrations
> (SAP, supplier email, carrier tracking) are mocked functions that read
> from and write to local synthetic fixtures. No real API keys to external
> enterprise systems are used or required — only an `ANTHROPIC_API_KEY` for
> the Claude reasoning calls described below.

## Classification: Agentic Workflow, not an Autonomous Agent

The governing rule, enforced in code (not just in this document):

> Any step that commits cost, makes a promise, or changes a plan requires
> human approval before execution. Any step that only gathers or reads
> information may run autonomously.

Concretely, `pipeline/execution.py` — the only module allowed to call the
mocked "commit" functions (`mock_send_sap_update`, `mock_book_freight`,
`mock_issue_spot_buy`, `mock_request_capacity`, `mock_reallocate_plan`) —
refuses to run unless it is given a `HumanCheckpointDecision` that (a) is
for the exact same `case_id`, and (b) has `approved=True`. `approved=True`
can itself only exist on a `HumanCheckpointDecision` that carries a
non-empty, fully-approved list of logged `ApprovalRecord`s (this is a
pydantic validator on the schema itself, not just a runtime check), so
there is no way to fabricate an approved decision without the logged
approvals to back it. This is asserted by `tests/test_hard_constraint.py`.

## Pipeline stages -> modules

| Spec section | Module | Nature |
|---|---|---|
| 3.1 Trigger | `pipeline/trigger.py` | deterministic |
| 3.2 Lead-time band routing | `pipeline/lead_time_routing.py` | deterministic, config-driven |
| 3.3 Root-cause triage | `pipeline/triage.py` | AI, fast/cheap tier (`TRIAGE_MODEL`) |
| 3.4 Orchestrator dispatch | `pipeline/orchestrator.py` | deterministic |
| 3.5a Evidence gathering | `pipeline/specialists/{supplier_capacity,upstream_supply,transport,demand_deviation}.py` + `pipeline/specialists/mock_tools.py` | autonomous, logged |
| 3.5b Evidence guardrail | `pipeline/guardrails.py::evidence_guardrail` | deterministic exclusion-list check |
| 3.5c Diagnosis + action proposal | same specialist modules, via `pipeline/specialists/base.py::call_diagnosis_llm` | AI, reasoning tier (`REASONING_MODEL`) |
| 3.6 Action guardrail | `pipeline/guardrails.py::run_action_guardrail` | AI, reasoning tier, low temperature |
| 3.7 Action synthesis | `pipeline/synthesis.py` | AI ranks/recommends; `impact_tier` computed deterministically afterward |
| 3.8 Human checkpoint | `pipeline/human_checkpoint.py` | CLI-simulated, mandatory, tiered |
| 3.9 Execution | `pipeline/execution.py` | deterministic; hard-gated on 3.8 |
| 3.10 Case log + recurring risk | `pipeline/case_log.py` | SQLite persistence; recurring-risk is a plain SQL count, not AI |

Shared infrastructure:

- `schemas.py` — every pydantic model referenced above; every LLM call in
  the system validates its JSON response against one of these before
  anything downstream trusts it.
- `pipeline/llm_client.py` — the one place that calls the `anthropic` SDK.
  Model names come from `TRIAGE_MODEL` / `REASONING_MODEL` env vars only,
  never hardcoded; on invalid JSON or a schema violation the model gets one
  corrective turn before the call raises.
- `pipeline/data_access.py` — read layer over the synthetic fixtures in
  `data/`, standing in for SAP/MRP/master-data reads.
- `config.yaml` — every threshold in the spec (coverage horizon rule,
  dispatch likelihood threshold, cost/impact threshold, recurring-risk
  count and window, evidence-guardrail exclusion list) in one place.

## Setup

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

export ANTHROPIC_API_KEY=sk-ant-...
export TRIAGE_MODEL=claude-...        # fast/cheap tier, e.g. a Haiku-class model
export REASONING_MODEL=claude-...     # stronger reasoning tier, e.g. a Sonnet-class model

python generate_mock_data.py          # (re)generates data/*.json
```

## Running it

```bash
# Live: scans the mock data for whatever currently trips the trigger and
# runs each case through the full pipeline with real interactive CLI
# approval prompts.
python main.py

# Scripted, reproducible walkthroughs of the three (+1 optional) required
# demo scenarios from Section 6:
python demo_scenarios.py low_impact
python demo_scenarios.py high_impact
python demo_scenarios.py guardrail_rejection
python demo_scenarios.py recurring_risk
python demo_scenarios.py all
```

`demo_scenarios.py` uses hand-crafted `DEMO-PN-*` fixtures (see
`generate_mock_data.py`) so each scenario's *shape* — lead-time band, which
signals are present, whether the case is forced to affect a committed
schedule — is reproducible run to run. What each specialist actually
diagnoses, and what the guardrails and synthesis decide, are still real,
unscripted Anthropic API calls; nothing about diagnosis or guardrail
content is string-matched or hardcoded. The one exception is documented
inline in `demo_scenarios.py::scenario_guardrail_rejection`: to reliably
demonstrate the action guardrail's cross-branch contradiction check without
depending on two live branches happening to disagree on a given run, that
scenario injects one clearly-labeled synthetic diagnosis (not a live LLM
call) alongside the live ones before the real guardrail evaluates all of
them together.

## Tests

```bash
python -m pytest tests/ -v
```

- `tests/test_hard_constraint.py` — asserts the Section 2/8 hard
  constraint: `execution.execute()` refuses to run without a matching,
  logged, fully-approved `HumanCheckpointDecision`; the schema itself
  rejects an "approved" decision that isn't backed by logged approvals;
  low-impact cases get exactly one planner prompt, high-impact cases get
  exactly three sequential role prompts, and any single rejection blocks
  execution. Runs with no API key required.
- `tests/test_pipeline_with_mocked_llm.py` — exercises the full pipeline
  wiring (schema validation, dispatch, evidence guardrail, action
  guardrail, synthesis, checkpoint, execution) with the Anthropic client
  substituted for a scripted fake, so the plumbing between every stage is
  verified without a real API key or network access. This is a test of the
  pipeline's glue code, not a substitute for running `main.py` /
  `demo_scenarios.py` against the real model.

## Known limitations of this prototype

- Demo scenario outcomes reflect real, temperature-0 reasoning-tier model
  behavior given the crafted synthetic signals — the *shape* of each
  scenario (lead-time band, impact tier, which branches dispatch) is
  deterministically engineered, but the model's specific diagnosis text and
  cost estimates are genuine reasoning output and can vary slightly between
  runs and between model versions.
- The `affects_committed_schedule` flag (Section 3.7) is a stub boolean
  input on `ShortageCase`; in a real deployment this would come from an
  APS/MRP system rather than being set by the caller.
- The evidence guardrail's exclusion list and other-supplier-name check are
  a defense-in-depth pattern check, not a substitute for the fact that both
  outbound branches already only ever send a fixed, pre-approved template.
